# Dart Patterns in Navis

## Where patterns fit in this codebase

- **Freezed / sealed state unions:** model states generated by freezed 4 form
  sealed hierarchies; switch expressions over them give compile-time
  exhaustiveness. Adding a variant then breaks every non-exhaustive switch —
  that is the point.
- **`AsyncValue` handling:** every `AsyncValue` consumer must handle loading,
  data, and error (repo rule). Prefer an exhaustive switch expression over the
  guard-clause ladder when producing a widget or value.
- **Dynamic payloads:** OpenSubsonic extension fields and loosely typed server
  responses are where map/list patterns genuinely earn their keep; strongly
  typed models in `lib/src/api/` go through json_serializable instead.
- **Records:** return `(a, b)` from helpers and destructure
  `final (a, b) = ...;` instead of out-parameters or wrapper classes.

## Switch statements vs expressions

- Producing a value → **switch expression**: `switch (v) { pattern => expr }` —
  must be exhaustive, no fallthrough.
- Side effects → **switch statement**: empty cases fall through, non-empty
  cases break implicitly.

## Selection strategy

- Polymorphic handling → Object patterns over `sealed` classes
  (`Foo(:var field) => ...`).
- Schema validation of dynamic maps → Map patterns (`{'id': final String id}`),
  remembering a map pattern checks `containsKey` — an **omitted** key fails to
  match even with a nullable value type. Extract truly optional keys directly
  (`map['key'] as String?`).
- Ranges/conditions in multi-arm switches → relational (`>= 1008`) and
  logical-or patterns; shared bodies via `||` (both sides must bind identical
  variables); refine with `when` guards.

## Anti-patterns (keep patterns earning their keep)

- Single-variable type promotion: use `if (x is T)`, not `if (x case T t)`.
- Standalone scalar comparisons: use `if (code >= 200 && code < 300)`, not
  `if (code case >= 200 && < 300)` — reserve relational patterns for multi-arm
  switch tables.
- Boolean switches: use `cond ? a : b`.
- Single-property reads: `user.name`, not `final User(:name) = user;`.
- **Silent data dropping:** do not use `if-case` in deserialization loops to
  skip malformed items when the payload is supposed to be well-formed — throw
  a `FormatException` with the offending value. Swallowed errors are a repo
  no-no.
- Redundant null arms: if `null` and `T` are handled identically, match
  `final T?` in one arm.

## Verify

1. `flutter analyze --no-fatal-infos` — exhaustiveness errors and unreachable
   arms surface here.
2. Dynamic map-pattern behavior (omitted vs explicit `null` keys) is invisible
   to the analyzer: add a unit test for the omitted-key case (see
   `dart-add-unit-test`).
3. `make gen` after touching freezed models, then rerun the affected tests —
   note the known Drift AOT interaction with new freezed models in this repo
   before modeling brand-new persisted types as freezed.
